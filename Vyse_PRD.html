01 Executive Summary

Vyse is a real-time AI workplace safety platform that watches live camera feeds the way a seasoned safety officer would — except it never blinks, never fatigues, and processes every pixel simultaneously. It combines YOLOv8 object detection for PPE compliance and hazard recognition with MediaPipe facial landmark analysis for drowsiness detection, all orchestrated through a 4-agent autonomous system that converts raw frame-by-frame detections into structured, high-level safety incidents.

The project is directly inspired by Motive's AI Vision platform — which pioneered computer vision for fleet safety and has seen exponential demand — and targets the broader industrial/workplace safety vertical where the same pattern (multi-camera + real-time CV + agentic decision-making) is worth billions. The global workplace safety technology market stands at $21.25 billion in 2025, heading toward $37.9 billion by 2030 at a 12.27% CAGR, with the AI video analytics segment alone growing at 22.7% CAGR.

Strategic Positioning
Vyse is built as an open, edge-deployable, privacy-first alternative to SaaS-only platforms like Protex AI ($36M Series B) and Voxel AI — differentiated by its transparent multi-agent architecture, developer-extensible rules engine, and ability to run fully on-premises on commodity hardware without cloud dependency.

Design Philosophy

Context-Aware

A single missing helmet is a warning. A missing helmet near a forklift at shift-start is a critical incident. Vyse understands temporal and spatial context.

Edge-First

Sensitive video footage stays on-premises. Inference runs locally. Only structured metadata — not raw video — leaves the facility.

Modular by Design

Each detection type, agent, and alerting channel is a swappable module. Add a new detection model without touching the rest of the system.

Explainable

Every alert includes the rule that triggered it, the confidence score, and the temporal window. Safety managers see reasoning, not black boxes.

YOLOv8 (released 2023) made real-time object detection cheap and fast enough to run on a single GPU or even a well-provisioned CPU. MediaPipe's face mesh landmark model (468 landmarks at 30+ FPS) made drowsiness detection accessible without custom datasets. The combination of these open-source primitives with Python's asyncio ecosystem makes a production-grade, multi-agent video pipeline achievable for a solo developer in weeks — something that would have required a team and 12 months just 3 years ago.

04 Problem Statement

Primary Problems

  • Manual PPE auditing doesn't scale. A single safety officer cannot monitor all zones across an 8-hour shift. Spot checks create compliance theater, not compliance.
  • Drowsiness is invisible until it's too late. Fatigue-related accidents cost lives, but there's no non-invasive, always-on detection method in most workplaces.
  • Incident reports are retrospective. Today's systems log incidents after they happen. The goal is prevention — catching the precursor before the injury.
  • Existing AI solutions are expensive and locked-in. Enterprise platforms like Intenseye, Protex AI, and Voxel AI require cloud subscriptions, proprietary hardware, and vendor lock-in starting at $50K+/year.
  • False positives erode trust. Naive frame-by-frame detection (someone removes their helmet for 2 seconds to scratch their head) floods safety managers with noise, causing alert fatigue.
Critical Insight
The gap is not in detection capability — YOLOv8 can detect a helmet reliably. The gap is in decision intelligence: converting thousands of detections per minute into a handful of actionable, prioritized, context-aware incidents. This is Vyse's core value proposition.

05 Solution Overview

Vyse is a Python-based, real-time safety intelligence system. It ingests live video from one or more cameras, runs concurrent detection models, and passes structured detection events through a chain of four specialized AI agents. Each agent has a single responsibility: detect, reason, alert, or analyze.

What Vyse Detects

PPE Compliance

Hard hats, safety vests, gloves, goggles, face shields — per-worker, per-zone compliance tracking in real time.

Drowsiness / Fatigue

Eye Aspect Ratio (EAR) via MediaPipe 468-landmark face mesh. Continuous blink-rate and eye-closure duration monitoring.

Unauthorized Device Usage

Mobile phone detection in restricted or safety-critical zones (machinery operation areas, controlled rooms).

Restricted Zone Breach

Polygon-defined exclusion zones. Alerts when persons enter hazardous areas without clearance.

Anomalous Posture / Fall

Unusual body posture detection using skeletal keypoint analysis — potential fall or incapacitation indicators.

Near-Miss Events

Proximity analysis between workers and moving equipment or vehicles within defined safety margins.

How It Works — The 4-Agent Pipeline

Raw video frames flow through an asynchronous producer-consumer pipeline. The Vision Agent ingests frames, runs YOLOv8 and MediaPipe in parallel, and emits structured detection events onto an internal message bus. The Risk Agent applies temporal rules to those events, converting transient detections into durable incidents with severity scores. The Alert Agent consumes high-severity incidents and dispatches notifications through configured channels. The Analytics Agent continuously writes to a time-series store for trend analysis and compliance reporting.

09 Feature Requirements

Feature requirements are organized by agent. Each agent owns a specific responsibility layer in the system. All agents communicate asynchronously via an internal event bus.

9.1 Vision Agent

Vision Frame Ingestion & Multi-Model Detection

Core Responsibilities

  • Capture frames from RTSP stream / webcam / video file at configurable FPS (default: 15 FPS inference)
  • Run YOLOv8n (nano) for real-time object detection — persons, helmets, vests, gloves, goggles, mobile phones
  • Run MediaPipe Face Mesh on all detected person ROIs to compute Eye Aspect Ratio (EAR)
  • Run skeletal pose estimation (MediaPipe Pose) for fall / anomalous posture detection
  • Perform zone overlap analysis using pre-configured polygon coordinates
  • Emit structured DetectionEvent objects onto the internal async queue

Detection Specifications

  • PPE Classes: person, helmet, no-helmet, vest, no-vest, gloves, goggles, phone
  • EAR Drowsiness Threshold: EAR < 0.25 for > 2 consecutive seconds = drowsiness flag
  • Confidence Threshold: Minimum 0.45 for detection events to be emitted (configurable)
  • Zone Breach: Centroid of detected person bounding box inside polygon = breach event
  • Frame Skip: Process every N-th frame for non-GPU environments (configurable, default N=2)

Non-Functional

  • Target: < 80ms inference latency per frame on GPU (RTX 3060+), < 250ms on CPU
  • Pipeline must not block on slow consumers — use asyncio Queue with backpressure
  • Annotated preview frames written to shared memory buffer for dashboard streaming

9.2 Risk Agent

Risk Temporal Rule Engine & Incident Scoring

Core Responsibilities

  • Consume DetectionEvent stream from Vision Agent
  • Maintain sliding time-window state per detection type per zone (default: 10-second windows)
  • Apply configurable temporal rules to convert detection sequences into Incident objects
  • Assign severity scores (LOW / MEDIUM / HIGH / CRITICAL) based on rule weight and context
  • Suppress duplicate incidents within a cooldown period (default: 60 seconds per worker per type)
  • Emit IncidentEvent objects onto the alert queue

Rule Engine Specifications

Rules are defined in a YAML config file and evaluated as a condition-action pipeline:

rules:
  - id: PPE_NO_HELMET_SUSTAINED
    trigger: no-helmet
    window_seconds: 8
    min_occurrences: 12        # 12/16 frames in 8s
    severity: HIGH
    cooldown_seconds: 120
    context_boosts:
      - condition: zone == "machinery"
        severity_upgrade: CRITICAL

  - id: DROWSY_DRIVER
    trigger: ear_low
    window_seconds: 3
    min_occurrences: 45        # ~15 FPS × 3s
    severity: CRITICAL
    cooldown_seconds: 300

  - id: PHONE_USAGE_MACHINERY
    trigger: phone_detected
    zone: machinery
    window_seconds: 5
    min_occurrences: 8
    severity: HIGH
    cooldown_seconds: 60

9.3 Alert Agent

Alert Multi-Channel Notification & Escalation

Core Responsibilities

  • Consume IncidentEvent objects from Risk Agent queue
  • Route incidents to appropriate channels based on severity and zone configuration
  • Manage alert deduplication, rate limiting, and escalation chains
  • Persist all alert dispatches to the incident log with delivery status

Alert Channels (v1)

  • Console Logger: Colored, structured terminal output for all incidents (all severities)
  • Webhook: HTTP POST with JSON payload to configurable endpoints (Slack, Teams, custom)
  • Email (SMTP): HTML email with incident details and annotated frame snapshot for HIGH/CRITICAL
  • WebSocket Push: Real-time incident stream to connected dashboard clients

Escalation Logic

  • CRITICAL incidents unacknowledged for 60 seconds → escalate to secondary contact
  • 3 HIGH incidents in same zone within 10 minutes → auto-elevate zone to CRITICAL monitoring mode
  • Alert deduplication: same incident type + same zone = suppress for cooldown window

9.4 Analytics Agent

Analytics Incident Intelligence & Compliance Reporting

Core Responsibilities

  • Subscribe to all incident events and write to time-series datastore (SQLite → PostgreSQL)
  • Compute rolling aggregations: incidents per hour, per zone, per shift, per type
  • Generate daily/weekly compliance summary reports (JSON + HTML)
  • Expose analytics query API for dashboard and external integrations
  • Maintain detection confidence histograms and model performance metrics

Analytics Dimensions

  • Time: Hourly, daily, weekly, monthly aggregations
  • Zone: Incident breakdown per configured zone
  • Type: PPE, drowsiness, device, breach, anomaly
  • Severity: Distribution across LOW/MEDIUM/HIGH/CRITICAL
  • Shift: Configurable shift windows (e.g. 6am–2pm, 2pm–10pm)
  • Model Health: Avg confidence, frame processing rate, queue depth

Agent Communication Protocol

Agents communicate exclusively through typed Python dataclasses passed over asyncio.Queue objects. No shared mutable state. Each agent runs as a separate asyncio coroutine. The pattern is a classic producer-consumer pipeline with backpressure.

from dataclasses import dataclass, field
from datetime import datetime
from enum import Enum
from typing import Optional, List, Dict, Any

class Severity(Enum):
    LOW = 1
    MEDIUM = 2
    HIGH = 3
    CRITICAL = 4

@dataclass
class DetectionEvent:
    frame_id: int
    timestamp: datetime
    camera_id: str
    detection_type: str          # "no-helmet", "ear_low", "phone", "zone_breach"
    confidence: float
    bbox: tuple                  # (x1, y1, x2, y2)
    zone: Optional[str]
    metadata: Dict[str, Any]     # EAR value, zone_id, etc.

@dataclass
class Incident:
    incident_id: str
    created_at: datetime
    camera_id: str
    zone: Optional[str]
    incident_type: str
    severity: Severity
    trigger_events: List[DetectionEvent]
    rule_id: str
    frame_snapshot_path: Optional[str]
    acknowledged: bool = False

Async Video Inference Pipeline

The pipeline uses Python's asyncio with strategic executor offloading for CPU/GPU-bound work (YOLO inference) to avoid blocking the event loop:

import asyncio
import cv2
from concurrent.futures import ThreadPoolExecutor

class VisionAgent:
    def __init__(self, camera_url: str, detection_queue: asyncio.Queue):
        self.cap = cv2.VideoCapture(camera_url)
        self.queue = detection_queue
        self.executor = ThreadPoolExecutor(max_workers=2)
        self.yolo = YOLO("yolov8n.pt")
        self.mp_face = mp.solutions.face_mesh.FaceMesh(...)

    async def run(self):
        loop = asyncio.get_event_loop()
        while True:
            ret, frame = self.cap.read()
            if not ret:
                await asyncio.sleep(0.01)
                continue

            # Offload CPU/GPU inference to thread pool
            yolo_results, face_results = await asyncio.gather(
                loop.run_in_executor(self.executor, self._run_yolo, frame),
                loop.run_in_executor(self.executor, self._run_mediapipe, frame)
            )

            events = self._parse_results(yolo_results, face_results, frame)
            for event in events:
                await self.queue.put(event)   # backpressure if queue full

14 Non-Functional Requirements

Performance

MetricTarget (GPU)Target (CPU)
Inference latency per frame< 80ms (YOLOv8n)< 250ms
End-to-end detection → incident< 500ms< 1.5s
Alert dispatch (webhook)< 200ms from incident< 200ms from incident
Dashboard feed latency< 150ms (WebSocket)< 300ms
API response time (incidents list)< 100ms (p99)< 100ms (p99)

Scalability

  • Single-camera support in v1.0; design must accommodate N-camera fan-out in v1.1 (one Vision Agent coroutine per camera)
  • Detection event volume: up to 15 FPS × 10 cameras = 150 events/second — asyncio Queue handles this without external message broker in v1
  • Incident database must efficiently query 100K+ records with pagination and indexed filters
  • PostgreSQL + TimescaleDB chosen for write-optimized time-series at scale

Reliability

  • Camera stream reconnect with exponential backoff (5 max retries before dead-letter alert)
  • Agent crash isolation: one agent panic must not bring down the orchestrator — wrap each in asyncio.TaskGroup with restart policy
  • All unacknowledged critical incidents must survive service restart (persisted before alert dispatch)
  • Graceful shutdown: drain queues before process exit, no lost in-flight incidents

Security & Privacy

  • No raw video leaves the local network — only structured metadata (bboxes, confidence, EAR values)
  • Frame snapshots stored locally with configurable retention policy (default: 30 days)
  • API endpoints protected with API key authentication (Bearer token) in production mode
  • Configurable face-blurring for non-safety-relevant zones (GDPR preparedness)

Observability

  • Structured JSON logs from all agents via structlog with agent name, camera ID, and incident ID as bound context
  • Prometheus-compatible metrics endpoint (/metrics) exposing: queue depths, frame processing rate, inference time histogram, incident count by severity
  • Health check endpoint (/health) for Docker health checks and load balancer probes
  • Model confidence histogram logged every 60 seconds to detect dataset drift

Vyse is built to span a 10× cost-and-capability range. A single facility can mix tiers — e.g. one beefy server for HQ and Jetson nodes at remote sites. Pick the tier that matches camera count and latency target.

Tier Hardware Cameras FPS / cam Inference Path Use Case
DEV Any modern laptop (M-series Mac, Ryzen, etc.) 1 5–10 YOLOv8n PyTorch CPU Local development, demos, recruiter calls
EDGE NVIDIA Jetson Orin Nano 8GB 1–2 15 YOLOv8n TensorRT FP16 Remote sites, no network egress, on-camera-pole deployment

Camera Specifications

  • Minimum: 1080p @ 15 FPS, H.264, RTSP over LAN. Most existing site cameras meet this.
  • Recommended: 4MP IP camera, 25 FPS, H.265, varifocal lens covering target zone, IR for night-shift.
  • Avoid: Wide-angle fisheye for PPE detection — distortion drops mAP by 8–12 percentage points unless lens-corrected upstream.
  • Network: Budget 2–4 Mbps per camera for direct RTSP ingest, or 0.3 Mbps if site does pre-encoding.

Deployment Modes

Local-Only (Air-Gapped)

All inference, storage, dashboard on one box. No cloud egress. For oil & gas, defense, hospitals.

Edge + Cloud Hybrid

Inference at edge; only structured incidents replicated to managed Postgres for cross-site analytics.

Managed SaaS (v2)

Site streams a thin gateway to Vyse cloud. Multi-tenant, per-camera billing. Series-A path.

BYO-Cloud

Customer deploys Vyse Helm chart to their own AKS/EKS/GKE cluster. Vyse provides chart + support.

Camera → Inference (≤80ms) → Risk Eval (≤30ms) → Persist Incident (≤50ms) → Alert Dispatch (≤200ms) → Dashboard Render (≤140ms) = ~500ms end-to-end on GPU. Every component has a hard p99 budget enforced via Prometheus.

20 MLOps & Dataset Strategy

The hardest part of a production CV system is not the first model — it's the second. Drift, edge cases, new PPE variants, and customer-specific gear all force retrains. Vyse treats data, models, and evaluation as first-class artifacts from day one.

Recommended Public Datasets (v1)

  • CHV (Color Helmet and Vest): ~2,500 images, helmets + vests in construction settings.
  • SHEL5K: 5,000 images, hard-hat focus, mixed lighting.
  • Roboflow Construction Safety: ~10,000 labeled images, mixed PPE classes — best single starter dataset.
  • NTHU Drowsy Driver Dataset: Annotated drowsiness for EAR threshold tuning.
  • WIDER FACE: Generic face dataset for robustness against helmet+mask occlusion.

Drift Detection & Retraining Loop

  • Confidence histogram: Analytics Agent logs detection-confidence histogram per class per day. If mean drops >10% week-over-week, fire MODEL_DRIFT alert.
  • Acknowledge-rate gap: If >30% of HIGH incidents in a zone are dismissed by safety manager, the rule or model in that zone is mis-calibrated — flag for review.
  • Per-camera health dashboard: FPS, missed-frame rate, average bbox count — anomalies flag camera-specific issues (lighting change, lens dirty, angle shifted).
  • Hard-negative mining: Frames where Risk Agent rejected a Vision detection are saved to data/hard_negatives/ for the next fine-tune cycle.

Evaluation Harness

Every model release must pass:

  • mAP@50 ≥ 0.88 on held-out PPE test set
  • Per-class precision ≥ 0.85 for helmet, vest (false-positive on safety gear is unacceptable)
  • EAR drowsiness recall ≥ 0.95 on NTHU subset
  • p99 inference latency ≤ tier target (80ms GPU / 250ms CPU)
  • No regression >2pp on prior release benchmarks

21 Design System & Brand Identity

Vyse's UI exists to make safety managers trust an AI's judgment about life-or-death events. That means dense-but-calm, dark-first, with motion reserved for what actually matters. The visual reference points are Linear (information density), Vercel (clarity), Datadog (incident-grade context), and Watchtower (camera-first layout).

Brand Pillars

Vigilant, Not Anxious

Critical alerts pulse; ambient operation is silent. Color and motion are budgeted — a CRITICAL incident must feel different from a HIGH.

Information Dense

Safety managers monitor multiple zones simultaneously. The UI shows more per screen than competitors without becoming noise — built for the operator, not the screenshot.

Explainable

Every alert traces back to a rule + confidence + window. The UI surfaces this on demand, not buried.

Keyboard-First

j/k to navigate incidents, x to acknowledge, e to escalate, / to search. Power users never leave the keyboard.

Motion Language (Framer Motion)

  • Page transitions: 180ms ease-out, fade + 4px y-translate. Never longer than 200ms.
  • Incident card enter: Slide-in from right + scale 0.98→1, 220ms spring. New incidents momentarily glow at their severity color.

  • Live feed bbox redraw: No animation — instant. Animating safety overlays creates dangerous perceptual lag.
  • Drawer slide: 240ms ease-out with backdrop fade. Esc closes.

  • <SeverityBadge /> — pill with severity color + label, uppercase mono.

International Standards

  • ISO 45001 (OH&S Management Systems): Vyse provides Clause 9.1 — Monitoring, Measurement, Analysis & Evaluation — automatic evidence collection.
  • ILO C155 / R164: Workplace safety convention — Vyse exports compliance summary in required reporting format.
  • EU Machinery Directive 2006/42/EC: Risk-assessment documentation generated from incident logs.
  • Pakistan Industrial Relations Ordinance / Sindh Factories Act: PPE compliance evidence for labor-department inspections.

Data Privacy

  • GDPR (EU) — Art. 6(1)(f) legitimate interest: Workplace safety is established lawful basis. Vyse documents this in DPA template.
  • GDPR Art. 9 — biometric: Drowsiness uses landmark geometry, NOT facial identity. EAR is a scalar, not biometric ID. Confirmed by external counsel before pilot.
  • CCPA / CPRA: Worker-notice template provided. Aggregate analytics by default; identity-linking is opt-in only.
  • Pakistan PDPB (when enacted): On-prem default deployment satisfies data-localization requirement.
  • Default retention: Raw frames 0 days, snapshots 30 days, incident records 2 years (configurable per customer DPA).

Audit Export Format

The Analytics Agent generates a signed monthly PDF + JSON bundle containing: total worker-hours observed, % compliant per zone per shift, incident count by severity, mean acknowledgement time, rules in force, model version. Bundle is hash-chained for tamper evidence.
